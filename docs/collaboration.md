# 多人协作流程

本文件是任务认领、并行开发和文档同步的单一规则来源。当前使用 `.scratch/auto-research-poc/issues/`；发布公共仓库后按任务 12 的迁移结果切换到 GitHub Issues。

Git 仓库已初始化并推送至公共 GitHub 仓库（`https://github.com/Crotes/AutoResearch`），分支、跨机器同步与 PR 并行协作流程自 2026-10-22 起启用。任务 12 的剩余事项（GitHub Issues 迁移、分支保护、CI 门禁、CODEOWNERS）完成前，任务跟踪仍使用 `.scratch/auto-research-poc/issues/`，评审通过 PR 进行。

## 认领任务

1. 查看任务的 `Blocked by`，确认所有依赖任务均为 `resolved`。
2. 选择编号最小的 `ready-for-agent` 任务。
3. 将 `Status` 改为 `claimed`，增加 `Owner: <GitHub 用户名或团队内唯一标识>`。
4. 先同步认领变更，再开始代码工作。看到其他 Owner 时选择另一任务。

一个任务同一时间只有一个 Owner。需要共同开发时，Owner 负责拆出互不重叠的子任务，并在父任务 `## Comments` 记录路径和负责人。

## 分支与并行边界

- 分支名采用 `<类型>/<任务编号>-<简短名称>`。
- 一个分支只解决一个任务；后续工作通过新任务表达。
- 并行任务优先按模块或文件边界拆分。必须修改同一契约时，由契约任务先合并，其他分支随后更新。
- 共享 Schema、领域枚举、端口接口和工作流状态属于高冲突区域；修改前在任务评论写明影响范围。
- 定期从主分支同步；冲突由当前分支 Owner 解决并重新运行完整检查。

## 交付循环

1. 认领任务并建立分支。
2. 写出或确认验收场景。
3. 实现最小完整变更，同时更新测试和对应文档。
4. 运行完整检查，在任务 `## Answer` 记录结果。
5. 创建 PR，等待非作者评审和 CI。
6. 合并后将任务标为 `resolved`，删除分支。

若工作发现范围扩大，保留当前任务边界并创建后续任务。若规格或 ADR 冲突，先记录冲突并取得团队决定，再继续实现。

## 文档同步矩阵

| 变更 | 同步位置 |
| --- | --- |
| 产品目标、范围、验收或工作流阶段 | `.scratch/auto-research-poc/spec.md` |
| 新领域概念、术语含义或禁用同义词 | `GLOSSARY.md` |
| 跨模块、长期或难以逆转的技术决策 | `docs/adr/` 新增 ADR |
| 模块职责、依赖方向或运行拓扑 | `docs/architecture/overview.md` |
| JSON 数据形状或跨进程契约 | `schemas/`、契约固定样例和契约测试 |
| 开发命令、环境要求或目录职责 | `docs/development.md`；必要时更新 `README.md` |
| 协作、认领、评审或发布流程 | `docs/collaboration.md` 或 `CONTRIBUTING.md` |
| 任务实现、偏差和验证结果 | 对应任务文件的 `## Comments` 与 `## Answer` |

一次变更可能命中多行。PR 作者逐项判断；不适用时在 PR 模板中说明原因。

## 评审重点

- **规格**：实现满足任务验收，没有静默扩大范围。
- **边界**：依赖方向正确，Pi 或存储细节没有泄漏到领域层。
- **可靠性**：检查点、重试、取消和错误分类仍可诊断。
- **证据**：重要研究结论可定位到来源版本和证据。
- **安全**：没有凭据、真实全文、内部反馈、Session 或日志进入仓库。
- **同步**：代码、测试、Schema、ADR 和使用说明没有相互矛盾。

评审意见标记为阻塞或建议。阻塞意见必须在合并前解决或由评审者明确撤销。

## 交接

中途交接时，Owner 在任务评论写明已完成内容、未完成内容、当前失败、验证命令和本地状态，再将 `Owner` 改为接手者。不要仅通过聊天传递关键上下文。
