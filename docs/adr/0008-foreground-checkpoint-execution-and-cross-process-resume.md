# ADR-0008：前台检查点执行与跨进程恢复

- 状态：已接受
- 日期：2026-10-23

## 背景

任务 09 要求研究者通过 CLI 完成「创建项目 → 启动运行 → 收集并生成速览 → 人工选源 → 详细解读与分类总结 → 终审 → 导出」。运行会跨越多次 CLI 调用，Agent 进程可能中断或需要换机器继续。与此同时，PoC 明确不引入后台 daemon、队列或常驻服务（任务 09 方案第十五节）。

如果继续沿用单进程内存模型，`status`、`review`、`resume`、`export` 只能在同一进程演示里工作，不是真正可用的 CLI。因此需要一个恢复模型，既允许跨进程继续，又不扩大为常驻服务。

## 决策

采用**前台执行到稳定检查点**的运行模型：

```text
CLI
 └─ ResearchWorkflow
     ├─ SQLite：业务事实、审核、事件、工件、检查点
     ├─ Pi Runtime：只负责当前阶段的 Agent 执行
     └─ Exporter：从 SQLite 重建并导出结果
```

行为约定：

- `run start` 阻塞到第一个审核闸门（选源）、失败或取消。
- `run resume` 阻塞到下一个审核闸门、完成或失败。
- 到达稳定状态后，`ResearchWorkflow` 把运行状态、`RunSpec`、审核决定和领域事件全部写入 SQLite，然后关闭 Pi 子进程。
- 下一次 CLI 调用从 SQLite 重建运行上下文，用 `RuntimeSnapshot` 恢复一个新的 Pi 进程并继续。
- Pi Session 只是执行上下文，不是业务事实源；会话目录仅作审计附件。
- `ResearchWorkflow` 是唯一写 `domain_events` 的方：drain runtime 事件流后按 `(run_id, sequence)` 幂等落库，恢复时重复 drain 不产生重复行。
- 终态运行的 `restore()` 仍会拉起一个空闲 Pi 进程以维持「每个恢复的运行都有进程上下文」的不变量，随后正常 dispose；这是不变量优先，不发送 prompt、不产生新事件。

本任务不实现常驻服务和后台队列。

## 后果

- 恢复、取消和导出都退化为「从 SQLite 读状态」，逻辑集中在 `ResearchWorkflow`，CLI、Pi Adapter 和 SQLite 不再各自复制业务规则。
- 前台阻塞意味着单个运行会占用一次终端调用直到稳定点；PoC 规模下可接受。
- 未来若需要服务化（后台运行、并发队列、定时研究），应新建 ADR 重新评估执行模型；本决策不绑定常驻进程。
- 跨进程恢复依赖 SQLite 是唯一事实源：任何未落库的内存状态（例如尚未 drain 的事件）在进程退出时丢失，因此稳定检查点必须覆盖「事件已持久化」这一条。
